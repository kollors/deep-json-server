# Переход с 0.9.0 на 1.0.0-rc.7

[English](MIGRATION.md) · [Актуальный README](README.ru.md)

Руководство сравнивает релиз `v0.9.0` с `1.0.0-rc.7` и также описывает изменения связей после RC6. Конфигурацию и клиентов нужно обновлять вместе. Требование Node.js 22 или новее сохраняется. Перед переходом скопируйте базу, конфигурацию, схему, загруженные файлы и их метаданные.

## 1. Выберите режим со схемой или без неё

Для REST без проверки по схеме и без генерации достаточно начать с такой замены:

```js
// 0.9.0
export default { database: { path: './database.json' } };
```

```js
// 1.0.0-rc.7
export default { storage: 'file', database: { source: './database.json' } };
```

REST без схемы и связи по именам хранимых полей `...Id` / `...Ids` сохраняются. Описанные ниже изменения запросов и ответов действуют и в этом режиме. Для OpenAPI и GraphQL теперь нужна явная схема моделей: генераторы больше не определяют поля по содержимому базы.

## 2. Обновите конфигурацию

| В 0.9.0 | В 1.0.0-rc.7 |
|---|---|
| `database.path` | `storage: 'file'` и `database.source` |
| `database.data` | `storage: 'memory'` и `database.source` |
| `database.schema` с `$info` / `$schema` | То же поле конфигурации, новый формат схемы с `models` |
| `files.directory` / `files.data` | `files.source` |
| `files.metadata` | Сохраните прежний путь к метаданным файлов |
| `openapi.path` | `openapi.target` |
| `$info` в схеме | `package.source`: `name`, `version`, необязательный `description` |
| `server.maxPageSize` по умолчанию `1000` | Теперь `100`; для прежнего ограничения задайте `1000` явно |

Обязательный `storage` действует на все источники, включая схему и метаданные пакета. В режиме `file` нужны пути, в `memory` — объекты и массивы. Смешивать дисковые источники и данные в памяти больше нельзя. Пути экспорта `target` остаются путями к файлам в обоих режимах.

Пример конфигурации с дисковой базой и экспортом OpenAPI:

```js
export default {
  storage: 'file',
  database: { source: './database.json', schema: './schema.json' },
  files: { source: './files', metadata: './files/_database.json' },
  openapi: { target: './generated/openapi.yaml' },
  package: { source: './package.json' },
  server: { maxPageSize: 1000 },
};
```

Создайте `schema.json` по следующему разделу. При настроенном `openapi` обязателен `package.source`: `name` пакета становится `info.title`, также используются `version` и необязательный `description`. Остальные свойства старого `$info` не имеют аналога в конфигурации. В памяти передавайте `package: { source: { name: 'example-api', version: '1.0.0' } }`.

**Сохраните прежний `files.metadata` явно.** Без него сервер выберет `<files.source>/.files.json` и не импортирует старый `_database.json`. Формат метаданных из 0.9.0 и маршруты `/_files/*` совместимы; заголовки загрузки бинарного тела и ответ `204` на удаление файла сохраняются.

Относительные пути по-прежнему отсчитываются от каталога конфигурации в CLI и от рабочего каталога при прямом вызове `createServer(config)`.

## 3. Замените дополнения к схеме полными моделями

В 0.9.0 `$schema` дополнял поля, определённые по данным. Это ещё не был нынешний формат моделей и связей. Теперь каждой коллекции нужна модель с `collection`, `fields` и одним первичным ключом верхнего уровня типа `string` или `number`.

| Старое описание | Новое описание |
|---|---|
| `$schema.users.name` | Имя модели в `models`, например `User` |
| `$schema.users.required: ['fullName']` | `fields.fullName.required: true` |
| `$schema.users.formats.bornAt: 'date'` | `fields.bornAt: { type: 'string', format: 'date' }` |
| Вложенные `properties` и `items` | Поля с типами, `[]` для массивов, пути через точку для дочерних полей |
| Автоматический строковый `id` | Явный `{ type: 'string', primary: true, generated: 'uuid' }` |

Опишите все хранимые поля, а не только прежние дополнения. Например, `actors` получает тип `object[]`, а `actors.fullName` — `string`. При явной схеме неизвестные поля и коллекции запрещены; исключение — автоматически выведенные ключи связей. Существующие записи проверяются при инициализации HTTP-сервера.

У полей со смешанными типами `oneOf` и ограничения «только целые числа» через `integer` нет общего прямого аналога. Приведите данные к поддерживаемому типу или оставьте REST без схемы. Имена моделей должны быть идентификаторами: старые имена компонентов с точками и дефисами нужно заменить.

### Полный пример с двусторонней связью

Для пользователей с полями `id`, `fullName`, `countryId` и стран с `id`, `name`:

```json
{
  "api": ["rest"],
  "models": {
    "User": {
      "collection": "users",
      "fields": {
        "id": { "type": "string", "primary": true, "generated": "uuid" },
        "fullName": { "type": "string", "required": true },
        "countryId": { "type": "string" },
        "country": { "type": "Country", "keyOn": "current" }
      }
    },
    "Country": {
      "collection": "countries",
      "fields": {
        "id": { "type": "string", "primary": true, "generated": "uuid" },
        "name": { "type": "string", "required": true },
        "users": { "type": "User[]", "keyOn": "related" }
      }
    }
  }
}
```

Каждая явная связь описывается с обеих сторон, везде обязателен `keyOn`. Сторона `current` хранит внешний ключ; `related` использует этот ключ в другой модели. Второй экземпляр ключа или хранимый массив `users` не нужен.

- У прямой связи `target` по умолчанию равен первичному ключу целевой модели. `source` выводится из имени поля связи и целевого ключа: `country` → `countryId`, `publishers` → `publisherIds`. При первичном ключе `ref` получится `publisherRefs`.
- У обратной связи пути меняются местами: для `Country.users` это `source: 'id'` и `target: 'countryId'`.
- Связь модели с собой: `Genre.parents: { type: 'Genre[]', keyOn: 'current' }` и `Genre.children: { type: 'Genre[]', keyOn: 'related' }` используют один хранимый массив `Genre.parentIds`.
- Если между моделями несколько связей, укажите, какие поля образуют пары: у обратной `Country.birthUsers` задайте `target: 'birthCountryId'`, у `Country.residenceUsers` — `target: 'residenceCountryId'`. Неоднозначные и отсутствующие пары отклоняются при загрузке.
- Объявляйте существующие ключи в `fields`, как в примере, если клиент их читает, фильтрует, сортирует или записывает. Автоматически выведенные ключи остаются в базе, но скрыты из обоих API и OpenAPI; выбрать их даже по имени нельзя.
- RC7 выводит массив источника и для списка с **непервичным** целевым полем. Например, `publishers` с `keyOn: 'current'` и `target: 'code'` получает `publisherCodes: { type: 'string[]' }`, если `Publisher.code` — строка. Объявите ключ явно, если его нужно открыть в API. Если RC6 сохранил такой автоматически выведенный ключ скаляром, перед обновлением преобразуйте значения в массивы, например `"A"` в `["A"]`. Явно объявленный скалярный ключ сохраняет свой тип.

До запуска исправьте ссылки на отсутствующие записи. Теперь запись проверяет целостность связей, а удаление целевой записи по умолчанию запрещено, пока на неё ссылаются. Задавайте `onDelete: 'cascade'` только там, где удаление цели должно удалять ссылающиеся записи. Обратная связь без явно указанного `onDelete` не добавляет собственного запрета.

### Сохраните идентификаторы и пользовательские поля

Не генерируйте идентификаторы заново. Старые строковые ID допустимы с `generated: 'uuid'`; UUID получают только новые значения. Если в коллекции есть и числа, и строки в качестве ID, перед подключением явной схемы приведите их и все ссылки к одному типу.

`primary` не включает `generated` автоматически. Без `generated` клиент сам передаёт ключ при создании. С `generated` клиент должен пропускать генерируемые поля: теперь их передача отклоняется, а не игнорируется, как в 0.9.0.

Старые поля приложения нужно объявить или осознанно удалить из копии базы. Пользовательский флаг архивирования не превращается в мягкое удаление автоматически. При включении дат, мягкого удаления или auth соответствующие служебные имена резервируются; переименуйте конфликтующие поля приложения заранее.

## 4. Выберите API и обновите команды запуска

Без корневого `api` сервер использует `['rest']`, а с секцией `graphql` — `['rest', 'graphql']`. Для доступа к базе только через GraphQL задайте `api: ['graphql']` и добавьте `graphql: {}`. Модель наследует корневой выбор или сужает его; `api: []` у модели скрывает её. Корневой `api: []` недопустим. Связанные модели должны разрешать одинаковые API.

Секцию `graphql` и GraphQL в корневом `api` нужно включать вместе. Auth и файлы остаются REST-сервисами и описываются только в OpenAPI. OpenAPI может описывать их и при базе, доступной только через GraphQL.

| Старый флаг CLI | Замена |
|---|---|
| `--files` | Уберите флаг: маршруты включает секция `files` |
| `--openapi` | `--generate` |
| `--openapi-only` | `--generate-only` |

В отличие от старого CLI, обычный запуск теперь включает настроенные файловые маршруты. Чтобы отключить их, уберите `files`. `openapi: {}` публикует `/openapi.json`, `graphql: {}` — `/graphql`. Для экспорта задайте `target` **каждому** настроенному формату: флаги генерации экспортируют все настроенные форматы. Обычный запуск файлы экспорта не записывает.

## 5. Переведите запросы и обработку ответов на scope

Единственный параметр запроса к записям — JSON `scope: [fields, arguments?]`, закодированный для URL.

| Параметр 0.9.0 | Запись в scope |
|---|---|
| `_where` или `fullName:contains=mi` | Второй объект: `where: { fullName: { contains: 'mi' } }` |
| `_sort=-id,fullName` | `order: [{ field: 'id', direction: 'DESC' }, { field: 'fullName', direction: 'ASC' }]` |
| `_page=1&_perPage=10` | `pager: { page: 1, pageSize: 10 }` |
| `_embed=country` | Первый объект: `country: [{ id: true, name: true }]` |

Пример для схемы выше:

```js
const scope = [
  { id: true, fullName: true, countryId: true, country: [{ id: true, name: true }] },
  {
    where: { fullName: { contains: 'mi' } },
    order: [{ field: 'fullName', direction: 'ASC' }],
    pager: { page: 1, pageSize: 10 },
  },
];
const url = `/users?${new URLSearchParams({ scope: JSON.stringify(scope) })}`;
```

Обновите и чтение ответов:

- Без `scope` и с `{ '*': true }` выбираются только скаляры, не хранящие ключи связей. Массивы, объекты, связи и объявленные ключи нужно выбирать явно. Поля `writeOnly` выбрать нельзя.
- Коллекции сохраняют `{ data, total }`. **Вложенные списки объектов и связей теперь тоже имеют `{ data, total }`**, а не обычный массив. Массивы примитивов остаются массивами. Одиночная связь возвращает объект или `null`.
- У каждого списка объектов есть пагинация, в том числе у вложенного: размер страницы по умолчанию `10`, максимум `100`. Раньше вложенные связи возвращались целиком. Задайте нужный `pager` каждому списку и загружайте следующие страницы.
- Фильтрация по связи работает без её выбора в ответе. Сортировка родительских записей по связанной модели, как старый `_sort=country.name`, не поддерживается. Сортируйте связанный список его собственным `order` либо храните сортируемое значение в родительской записи.
- Строковые сравнения `gt/gte/lt/lte` используют порядок без учёта регистра, с учётом числовых частей. Проверьте клиентов, полагавшихся на прежнее лексикографическое сравнение.
- JSON scope ограничен 10 000 символов и 32 уровнями выбора. Неизвестные поля и операторы отклоняются даже на пустых данных.

## 6. Проверьте запись и включение auth

`PATCH` объединяет поля верхнего уровня; переданный вложенный обычный объект заменяет прежний с сохранением защищённых полей. `PUT` заменяет доступные для записи поля, сохраняя первичный ключ, генерируемые, служебные и `readOnly` значения. При создании и замене нужны все обязательные поля без значений по умолчанию.

Поле связи принимает объекты, например `country: { id: '1' }`, а не скалярные ID. **Начиная с RC7 объект только с первичным ключом считается ссылкой в POST, PUT и PATCH.** Поля, даты и авторство целевой записи сохраняются. Дополнительные поля превращают его в обновление: PUT заменяет цель и требует её обязательные поля, POST/PATCH обновляют переданные поля. При изменении обратной связи нужны права на каждую запись, чей хранимый ключ меняется. Объявленные хранимые ключи, например `countryId`, тоже позволяют менять ссылки напрямую. Не передавайте одновременно связь и её хранимый ключ.

**При переходе с RC6:** объект только с ключом больше не обновляет цель, не меняет её даты/авторство и не требует владения неизменяемой целевой записью. Если клиент намерен обновить или заменить цель, передавайте поля для изменения. Объявленные хранимые ключи по-прежнему позволяют менять только ссылки.

Пропущенные обратные связи (`keyOn: 'related'`) сохраняются при PUT. Явное `users: []` меняет ключи пользователей, чтобы отсоединить их; операция может завершиться ошибкой при обязательных ключах или отсутствии прав. Вложенные изменения атомарны, а изменение общей целевой записи видно всем, кто на неё ссылается.

Auth, даты и мягкое удаление — новые необязательные возможности. Для первого перехода с сохранением записи без входа и физического удаления не добавляйте `auth`, оставьте `timestamps` / `softDelete` выключенными — это их значения по умолчанию.

Если включаете auth, создайте отдельное хранилище учётных записей и перенесите владельцев осознанно. Старые записи без `createdById` может менять только администратор. Через API владелец управляется сервером; подготовьте его в копии базы до запуска, если старые записи должны редактировать обычные пользователи. Auth не закрывает чтение и файловые операции. Сессии хранятся в памяти и заканчиваются при перезапуске.

При `softDelete` DELETE сохраняет запись, списки по умолчанию скрывают удалённые записи, чтение по первичному ключу может вернуть их, а успешный PUT/PATCH восстанавливает. Старый пользовательский флаг архивирования не преобразуется автоматически. Перед включением прочитайте [правила дат, удаления и владения](README.ru.md#даты-записей-удаление-и-владельцы).

## 7. Обновите программное использование

`createServer(config)` принимает ровно один аргумент. Уберите прежний второй аргумент `{ files: false }`; для отключения файлов уберите `files` из конфигурации.

`facade.openapi()` и `facade.graphql()` возвращают документы без записи в `target`. Нужны соответствующие секции конфигурации; для OpenAPI — также метаданные пакета и схема. Используйте флаги генерации CLI или явную запись:

```js
import { createServer } from '@kollors/deep-json-server';
import { writeOpenapi } from '@kollors/deep-json-server/openapi';
import config from './server.config.js';

const facade = await createServer(config);
await writeOpenapi(await facade.openapi(), './generated/openapi.yaml');
const app = facade.fastify();
await app.ready(); // Инициализация и проверка базы без открытия порта.
await app.close();
```

Одна генерация схем не проверяет существующие записи базы. Для инициализации HTTP и проверки данных вызовите `ready()`, `inject()` или `listen()`. После изменения моделей и запросов пересоздайте клиентов из новых OpenAPI/GraphQL-документов.

## 8. Проверьте переход и подготовьте откат

1. Зафиксируйте выбранную RC-версию и переведите **копию** файлов 0.9.0. Выполните генерацию, затем инициализацию HTTP-сервера для проверки данных.
2. Проверьте чтение по умолчанию, явные ключи, вложенные списки, фильтры и пагинацию. На одноразовых копиях записей проверьте создание, PATCH, PUT, изменение связей и удаление.
3. При включении auth проверьте владельца, администратора и обычного пользователя без владения на старых записях. Убедитесь, что загруженные файлы доступны через прежний путь к метаданным.
4. Перед переключением остановите старый сервер. Используйте один процесс для базы и файлового хранилища: новая версия блокирует дисковую базу. Для ручных правок останавливайте процесс.
5. Для отката храните вместе старую версию пакета, конфигурацию, схему, базу и метаданные файлов. Восстанавливайте их вместе; не направляйте 0.9.0 на данные, уже изменённые новым сервером. В последующие резервные копии включайте новые счётчики (`<database>.counters.json`) и служебные данные восстановления мягкого удаления, если используете эти функции.
